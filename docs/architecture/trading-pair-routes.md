# Trading Pair Routes: от пары площадок к проверенному VPN-маршруту

Дата: 2026-09-07. Статус: реализован первый релиз **расчётного** Pair Routes
на существующих gates, без новых серверов. Ниже сохранена целевая концепция;
перечень готового функционала и границы текущего релиза указаны отдельно.
Фактическую выкладку и проверки см. в runbook.

## Реализовано в первом релизе

- Четыре новые площадки на старой карте и в Pair Routes: Variational Omni,
  Extended, RISEx, Lighter. Итого 17 venue endpoints, включая 2 prediction
  venues; остальные chain/oracle targets остаются только на карте.
- `/trading/pairs`, alias `/trading/routes`: две группы площадок, тип пары,
  фиксированная точка, поиск, сортировки, все точки/лучшая точка для пары,
  отдельные legs, раскрытие маршрута, матрица и share URL. Нет инструментов.
- Schema-first public API `/v1/public/trading/pairs` и
  `/v1/public/trading/routes/:routeId`. Derived service использует существующие
  latest measurements и gate benchmarks; API-кэш на 15 секунд со singleflight.
  Пары не создают дополнительных jobs или запросов к площадкам.
- Только TCP-оценка по одному общему egress, revision/freshness/skew checks,
  запрет stale/offline/maintenance/same-metro N/A и потерь на gate-сегменте.
  В рекомендации допускаются только IPv4 measurements: текущий FullTunnel
  не покрывает IPv6. Семейство адреса передаётся без публикации самого IP;
  IPv6 direct samples остаются в карте и матрице, но не служат VPN baseline.
  VPN A/B verified всегда 0: measured filter честно показывает пустое состояние.
- Проверяемый сервером opaque route ID передаёт точные ingress/egress в
  обычный FullTunnel checkout, сохраняется через вход; устаревший preset
  отклоняется до новой оплаты. Повтор уже созданного payment request возвращает
  исходную сессию независимо от изменения рейтинга.
- Read-only Node.js client `trading-pair-check.mjs`: явные direct/VPN профили,
  ограниченные запросы к официальному каталогу, локальные отчёты и сравнение.
  Он НЕ устанавливает tunnel, НЕ меняет маршруты и НЕ доказывает underlay.
  VPN запускается пользователем в его подготовленном namespace. Результаты
  не загружаются в публичный рейтинг и не получают автоматически verified.
- Агент явно отклоняет неподдержанные network profiles вместо direct fallback;
  старая карта больше не показывает просроченные successful samples как Live.

Не входят в этот релиз: автоматический fleet tunnel A/B/provisioner,
подтверждённый p95/CI выигрыш, накопительная история 15m/1h/24h, warm HTTP/WS,
бесплатные пробные VPN, split/multi-egress, загрузка клиентских отчётов,
сохранённые пары, уведомления и маркетинговая event analytics. Эти пункты ниже —
дальнейший roadmap, а не обещание работающего функционала.

## Решение

Сделать отдельный **Pair Routes** по адресу `/trading/pairs`. Существующие
карта, разделы площадок и `/benchmarks` остаются. Пункт `Arb Routes`, который
сейчас ведёт на заглушку, после реализации ведёт на новый dashboard;
`/trading/routes` сохраняется как alias. Не превращать страницу в торговый
терминал: без инструментов, спредов, funding, ордеров и подключения биржевых
аккаунтов.

Единица выбора — **площадка A + площадка B + конкретный probe/server location
+ воспроизводимый профиль маршрутизации**. Ответ пользователю: «Из этой
точки вот так меняется отклик обеих площадок; вот маршрут, на котором это
проверено; вот как проверить его со своего сервера и получить конфиг».

Из [VOOI Arbitrage Desk](https://ultra.vooi.io/arbitrage-desk) заимствуем
принцип плотной сравнительной таблицы с фильтрами и действием в строке.
VOOI сравнивает торговые показатели инструментов; здесь предмет сравнения —
доступ к инфраструктуре площадок. Успех продукта — не количество красивых
зелёных строк, а переход от найденного маршрута к подтверждённому клиентскому
A/B-выигрышу и используемому конфигу.

Четыре новые цели увеличивают каталог до 30 targets и дают ещё 120 latest
строк при неизменных 30 production probes. После добавления имеется 10 CEX
и 5 perpDEX-площадок, то есть 105 неупорядоченных пар или 3 150 комбинаций
«пара × probe». Это вычисления из общей матрицы, не 3 150 отдельных
внешних бенчмарков. Prediction venues можно включать отдельным фильтром;
L2/RPC/oracle targets не считать торговыми площадками.

Важно: значительная часть CEX-целей сейчас относится к Spot/time APIs.
Наличие строки Binance или Coinbase не означает измерение их derivatives
order-entry. Перед позиционированием для perp↔perp нужен аудит нужных
product/API endpoints. Площадка, продукт, endpoint и роль endpoint — разные
сущности, даже если инструменты в интерфейсе не показываются.

## Интерфейс

Основной экран — таблица, дополнительный режим — матрица «локации × площадки»
для полного обзора без переключений. Матрица показывает тот же выбранный
класс измерений и окно, не смешивает DNS, REST и WebSocket. Карта остаётся
доступна по ссылке из названия площадки.

Фильтры:

- Две независимые группы площадок A/B с мультивыбором, поиском и пресетами
  `CEX ↔ perpDEX`, `perpDEX ↔ perpDEX`, `CEX ↔ CEX`.
- «Где работает бот»: город **и provider/probe**, не только флаг страны.
  «Исследовать все точки» — отдельный режим, не замена указанному серверу.
- Окно 15m / 1h / 24h; класс `Public API cold`, затем `Public API warm` и
  поддержанные `WS application RTT`; источник `Measured / Estimated`.
- По умолчанию только свежие подтверждённые улучшения без регрессии второй
  связи; отрицательные и неподтверждённые результаты доступны явно.
- Сортировки: выигрыш в ms (основная), в %, конечный отклик пары,
  надёжность. Больший выигрыш не обязательно означает меньшую итоговую задержку.

Пример компоновки ниже **полностью синтетический**, не рекламные/live данные:

| Площадки | Бот / probe | A: direct → HS | B: direct → HS | Суммарный индекс | Выигрыш | Действие |
| --- | --- | --- | --- | --- | --- | --- |
| Binance ↔ Lighter | Frankfurt / Provider X | 84 → 53 ms | 67 → 39 ms | 151 → 92 ms | 59 ms / 39% | Проверить мой сервер |
| Hyperliquid ↔ Extended | Amsterdam / Provider Y | 61 → 49 ms | 92 → 81 ms | 153 → 130 ms | 23 ms / 15% | Проверить мой сервер |

В реальной строке также компактно показывать возраст замера и статус качества.
Пару A/B канонизировать по venue ID: обратная перестановка не создаёт дубль.
В режиме всех точек группировать по паре и раскрывать все локации; в режиме
выбранного сервера не скрывать его под «лучшей точкой в мире».

Раскрытие строки — две колонки A и B, одинаковая шкала полос direct/HS,
выбранные endpoints/протоколы, p50/p95 и ошибки по каждой стороне,
число проб, график выигрыша по окнам и путь ingress→egress. Метки:
`Measured`, `Estimated`, `Stale`, `No improvement`, `Insufficient samples`,
`Unavailable from this location`. «Нет данных» не равно 0 ms. Старый successful
result не должен оставаться зелёным, если probe жив, но target давно не измерялся.

## Что считать выигрышем

### Подтверждённые значения

Один и тот же source S выполняет одинаковые read-only запросы к A и B
напрямую и через **реально созданный** профиль Hyperspace R. Для каждого
endpoint используются та же revision, тип подключения и сопоставимые окна.

Пусть `D_A`, `D_B`, `H_A`, `H_B` — медианы отклика соответствующих серий.
Основная понятная метрика:

```text
Pair response index direct = D_A + D_B
Pair response index HS     = H_A + H_B
Saved ms                  = (D_A + D_B) - (H_A + H_B)
Saved %                   = Saved ms / (D_A + D_B) × 100
Leg A saved               = D_A - H_A
Leg B saved               = D_B - H_B
```

Сумма медиан — **индекс**, не p50 реального арбитражного цикла и не время
исполнения двух ордеров. Она прозрачна для ранжирования одинаковых профилей
измерений, но не модель стратегии пользователя. Нельзя складывать p95 и
называть результат p95 пары. Если понадобится режим одновременного обращения,
собирать длительности обоих запросов в одном trial и распределение `max(A,B)`;
для последовательного синтетического теста — реальные trial sums. Это тоже
не latency fill/hedge: площадки не исполняют наши read-only пробы.

Не обнулять отрицательный выигрыш отдельной стороны. Положительный индекс
не даёт зелёную рекомендацию при подтверждённой регрессии одного leg, росте
ошибок или существенном ухудшении хвоста. Начальные quality gates для canary:
не менее 100 успешных сопоставимых trials на leg/profile, не менее 15 минут
наблюдения, явно показанный success ratio, положительная нижняя граница
95% block-bootstrap CI выигрыша. Это стартовые продуктовые настройки, не
универсальная статистическая гарантия. Таймауты/HTTP errors учитывать отдельно,
не выбрасывать из знаменателя и не назначать им успешную latency.

По умолчанию сортировать по `Saved ms` среди строк, прошедших quality gates.
Отдельно показывать выигрыш по окнам и его устойчивость за 24h. Не выдавать
одно удачное измерение за постоянное преимущество; отбор best routes проверять
на следующем независимом окне, чтобы не рекламировать случайный минимум.

### Расчётный потенциал из существующих данных

Для дешёвого поиска кандидатов использовать **TCP connection RTT proxy** из
trading probes и направленный gate RTT из benchmarks. В частном случае
source находится на ingress gate I:

```text
Estimated HS leg to A ≈ gate_DZ_RTT(I,E) + TCP_connect_RTT(E,A)
Estimated HS leg to B ≈ gate_DZ_RTT(I,E) + TCP_connect_RTT(E,B)
```

Это приближение сетевого пути, а не подтверждённый app RTT: разные транспорты,
ECMP/асимметрия, очередь, WireGuard overhead и CDN могут нарушать аддитивность.
Сравнивать его только с `TCP_connect_RTT(S,A/B)` той же методики, отдельно
от таблицы measured API-индексов. Не прибавлять один gate RTT к нынешнему
`totalP50Ms`: холодный TCP/TLS/HTTP запрос использует несколько сетевых обменов.
Не делить RTT пополам и не выдавать это за измеренную one-way latency.

Сервер клиента вне ingress добавляет участок S→I, который публичная карта
сейчас не измеряет. Совпадение города не означает совпадения ISP/маршрута.
До клиентского теста вывод — «из нашего probe», а не «с вашего сервера».

Маршрут для MVP имеет **один общий egress для обеих площадок**. Нельзя взять
лучший egress для A и другой для B и продать это как один существующий
FullTunnel-конфиг. Разные выходы / одна сторона напрямую — дальнейший
split-routing продукт с отдельными policy и измерениями.

### Как доказать именно DoubleZero

В canary сравнивать три профиля при одинаковом source:

1. Прямой Internet S→A/B.
2. Hyperspace/WireGuard с теми же ingress/egress, но public underlay.
3. Тот же Hyperspace путь через DoubleZero underlay.

Разница 1→3 — общий эффект продукта; 2→3 — эффект выбора DoubleZero при
сохранённом выходе. Сам по себе быстрый egress рядом с API этого не доказывает.
Третий профиль без второго не даёт причинно приписывать весь выигрыш DZ.
`same_doublezero_metro`, отсутствие подтверждения интерфейса/маршрута,
fallback на Internet или неготовый gate исключают ярлык `DZ verified`.

## Расширение инфраструктуры

Сохраняем текущие PostgreSQL, Fastify API, worker, independent trading agent
и systemd. Новый стек, брокер и отдельная база для MVP не нужны.

1. **Каталог и contracts.** Ввести стабильные venue IDs и связи venue→target,
   `endpointRole`, product, connection mode, target revision, display policy.
   Новые targets уже несут начальные metadata, но старые CEX/Hyperliquid нужно
   разметить и проверить. Не выводить названия бирж из category блокчейна.
   Явно связать probe node с gate ID; внутреннее `gate_id` уже есть, public
   payload его не отдаёт. Не парсить имена узлов для production join.
2. **Derived service.** Новый модуль `trading-pairs` в control-plane, public
   schemas сначала в `packages/contracts`. Worker строит cached snapshots;
   API `GET /v1/public/trading/pairs` поддерживает filters, pagination и sort.
   Row включает venue IDs, source, route/profile ID, target revisions,
   per-leg metrics, index, quality, oldest measuredAt и config eligibility.
3. **Freshness/история.** Проверять возраст каждого входного измерения,
   heartbeat и skew времён; начинать с TTL `max(90s, 3 × interval)` и не более
   одного interval между входами оценочной строки. Для verified — единые trial
   IDs/окна. Не использовать `generatedAt` API как время измерения.
   Хранить short-retention raw trials либо mergeable histograms плюс error
   counts; настоящие 5m rollups не должны перезаписываться последним отчётом.
   Версионировать методику и не склеивать warm/cold или разные target revisions.
4. **Profiles и безопасность.** Расширить scheduler/agent с `direct` до
   явных provisioned profiles. Одной строки `networkProfile="doublezero"`
   недостаточно: текущий execute не выбирает по ней транспорт. Измерительный
   процесс остаётся непривилегированным; namespace/маршрут готовит отдельный
   ограниченный provisioner на dedicated testnode. Потерянный tunnel должен
   давать ошибку, а не незаметный direct fallback. Подтверждать policy route,
   интерфейсы/счётчики, handshake, egress и действительную DZ-доступность.
   Не менять default route хоста с клиентскими VPN-сессиями.
5. **Измерительная методика.** Сначала одинаковый cold HTTP A/B с честной
   маркировкой; затем persistent HTTP и протокольно подтверждённый WS
   request/reply на допускающих это API. Подписка до первого случайного tick
   не является RTT: включает частоту событий/батчинг. Ни metadata API,
   ни WS ping не равны order-entry. Фиксировать resolved IP, DNS policy,
   payload size/cache headers и reconnect. Natural DNS полезен для реального
   пользовательского эффекта, pinned IP — отдельный контролируемый эксперимент
   с тем же SNI, не смешиваемый с ним.
6. **Бюджет.** Сохранять N×venues direct baseline; вычислять все пары из него.
   По gate matrix выбирать ограниченный top-K route candidates, затем
   проверять их реальным tunnel A/B на нескольких testnodes. Кэшировать
   измерение source/profile/target для всех пар, где оно используется.
   Общий limiter по venue и egress IP, jitter, 429 backoff, concurrency/bytes
   budget; shared NAT и несколько окружений учитываются вместе.

## Путь к конфигу и покупке

1. Публичный dashboard без регистрации: выбрать площадки/точку, увидеть
   evidence. Share URL содержит только публичные filters, не API/WG keys.
2. «Проверить мой сервер»: сохранить выбранную пару/profile в draft и пройти
   существующую авторизацию с возвратом. Публичный A/B с нашего probe остаётся
   доступен без авторизации. Клиентский тест — подписанный проверяемый
   CLI/инструкция на добровольно указанном сервере, без exchange credentials
   и без автоматической отправки сделок. Одного browser RTT недостаточно.
3. Пробный tunnel использует тот же lifecycle временной VPN-сессии с quota,
   TTL и cleanup. Бесплатность и её billing policy — отдельное решение, не
   скрытый обход оплаты. Пока такой тест не реализован, CTA ведёт на
   настройку конфига с явным «выигрыш на вашем сервере не проверен».
4. Подтверждение показывает direct/HS на клиентском source, ingress/egress,
   scope маршрутизации, текущую цену/период и ограничения доступа площадок.
   Server-side opaque `routePresetId` разрешается заново: fresh data,
   schedulable gates (не Maintenance), нужное окружение DZ, capacity и policy.
   Не доверять gate ID, цене и выгоде из query string и не менять маршрут
   незаметно после измерения.
5. Существующий checkout/баланс → выпуск WireGuard-конфига → скачивание →
   повторный read-only A/B на сервере. Если результат уже отрицательный,
   показать это и предложить перепроверку, а не сохранять обещание ускорения.

Для первого end-to-end продукта один FullTunnel внутри namespace торгового
бота совместим с существующей моделью одного egress. Явно предупреждать,
что весь трафик **этого namespace** пойдёт через VPN, а не только две биржи.
Не включать FullTunnel на production-хосте автоматически.
Текущий `IpToIp` с одним IPv4 `/32` не является «конфигом для двух площадок»:
API имеют несколько адресов, DNS/CDN меняются, есть IPv6 и дополнительные
WS/auth endpoints. Для будущего venue-only split tunnel нужны несколько
AllowedIPs, обновление DNS/routing policy, политика IPv6 и тесты утечек;
это отдельное изменение contracts и dataplane.

## Очерёдность и критерии готовности

**A. Расширение каталога (эта ветка).** Четыре публичных API + навигация,
allowlists и 1 MiB body cap агента. Порядок canary/promote и эксплуатационные
ограничения — в [runbook](../runbooks/trading-latency-probes.md).

**B. Полный board + поиск кандидатов.** Venue filters, два leg в строке,
фиксированный source, матрица, cache/API/freshness, расчётные маршруты
отдельно от измеренных. При отсутствии tunneled samples писать
`No verified routes yet`, не рисовать выдуманную зелёную выгоду.
Это уже закрывает задачу «увидеть несколько площадок без перекликивания».

**C. Проверенный выигрыш.** Сначала небольшой canary source×egress×venues,
три профиля, persistent connections, raw trials/rollups, rate limits и
проверка отсутствия влияния на VPN gates. Маркетинговый запуск раздела
«ускорение» — после этого, а не после одной оценочной формулы.

**D. Конверсия.** Route presets, возврат из login, совместимость FullTunnel,
клиентский self-test/TTL и повторный замер после активации. Дальше — сохранённые
пары и opt-in уведомления «появился устойчиво лучший маршрут».

Acceptance tests: пары A/A запрещены; A/B и B/A не дублируются; offline,
stale, HTTP 403/451/429 и нулевой baseline не получают positive score; рост
ошибок или регрессия второго leg не скрывается; профили/ревизии не смешиваются;
same-metro DZ N/A не становится нулём; недоступный gate не продаётся;
потерянный tunnel не измеряется как direct; old map и конфиг issuance работают
при выключенном paired subsystem; checkout воспроизводит измеренный маршрут.

## Маркетинг и продуктовая проверка

Позиционирование: **«Найдите более быстрый сетевой маршрут для своей пары
площадок — и проверьте его на своём сервере»**. Не «найдите прибыльный арбитраж»,
не обещание большего объёма, APR, исполнения или отсутствия проскальзывания.
Не рекламировать обход географических ограничений площадок.

Публичные landing/share pages по паре и региону, с явно указанными протоколом,
периодом измерений и provenance. CTA из каждой карточки ведёт на тот же
сохранённый маршрут. Начальные сегменты: операторы multi-venue ботов,
delta-neutral/basis трейдеры, небольшие market-making команды и сообщества
пользователей perpDEX. Пользовательские отзывы/клиентские измерения публиковать
только с согласием, не переносить частную переписку в open-source материалы.

Пилот: 3–5 команд сообщают пары, реальные регионы/провайдеров, используемые
REST/WS API и допустимое ухудшение хвоста. Сначала измерить их пути, затем
выбрать case studies. Считать воронку `pair_view → route_detail → test_started
→ test_positive → checkout → config_active → retained_7d`, отдельно долю
клиентов с подтверждённым A/B-выигрышем. Сам трафик VPN не доказывает торговый
объём; его и финансовый результат не выводим из сетевой телеметрии.
